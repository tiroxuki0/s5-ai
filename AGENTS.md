# Repository Guidelines

## Project Structure & Module Organization
`app/` hosts the App Router surfaces: `page.tsx` is the main search UI, `app/admin/` is the ingestion dashboard, and `app/api/s5/*` contains the hybrid search endpoints. Shared UI lives in `components/`; move widget-only pieces to `widget/components` to keep boundaries clear. `lib/` is the home for LangChain pipelines, Pinecone/Redis clients, and env utilities, while `public/` serves static assets plus the widget bundle generated by `build-widget.sh`. The `widget/` directory is a self-contained package for the embeddable chat widget.

## Build, Test, and Development Commands
Install dependencies once (`npm install` or `pnpm install`). `npm run dev` starts the Next dev server. `npm run build` produces the optimized `.next` output and `npm run start` previews it locally. `npm run lint` runs ESLint with the Next preset and is the current automated gate. Execute `./build-widget.sh` after touching the widget code; it bootstraps dependencies if needed, runs `npm run build` inside `widget/`, and copies `embed.js` plus `widget/widget.{js,css}` into `public/`.

## Coding Style & Naming Conventions
Strict TypeScript is enabled, so add explicit types on exported functions and prefer `const` + arrow components. Use 2-space indentation, PascalCase for React components/hooks, and verb-based camelCase helpers (`ingestConfluenceSpace`). Tailwind v4 drives styling—order utilities from layout to state, and tidy long class strings manually because no formatter is wired up. Always run `npm run lint` before committing.

## Testing Guidelines
There is no automated test suite yet, so manually verify flows with `npm run dev` and inspect server logs for LangChain/Brave responses. New tests should live next to their feature (`app/search/__tests__/search-handler.test.ts`) and use React Testing Library or lightweight API harnesses. Prioritize scenarios that exercise each search branch (internal, external, hybrid) plus ingestion tasks.

## Commit & Pull Request Guidelines
Commits follow the conventional style shown in `git log` (`feat:`, `fix:`, `chore:`) and should stay focused on a single change. Re-run lint and, if relevant, the widget build before pushing. PRs need a concise problem statement, bullet list of changes, screenshots or recordings for UI updates (`/admin`, search surface, widget), and the commands you ran. Link related issues and call out new env vars or deployment considerations.

## Security & Configuration Tips
Secrets belong in `.env.local`. Supply `BRAVE_API_KEY` and `GROQ_API_KEY`, plus Pinecone/OpenAI/Confluence/Redis keys when those features are enabled. Double-check `ENABLE_AI_SEARCH` and `ENABLE_EXTERNAL_SEARCH` before promoting a build, and verify that `public/embed.js` references the target domain prior to sharing the widget snippet.
